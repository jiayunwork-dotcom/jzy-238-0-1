海洋所沿岸上升流课题组每个季度都要交一份上升流指数报告：沿海岸布了二十多个测风站，小时风速风向一路累积，按风应力推算离岸方向的 Ekman 输运，再汇总成逐日、逐月的指数。现在的做法是季度末把全部风数据拖下来重跑一遍脚本，期间站点补传、仪器更正的数据又不断进来，报告交出去之后数字还会变，没人说得清变在哪。组长让我找人做个后端，我把他们的要求整理一下。

物理口径用经典的稳态 Ekman 理论：风应力由风速按块体公式换算，拖曳系数是否随风速变化由你决定，但一个系统里只能有一套口径、要写进文档并记在结果上；科氏参数由站点纬度确定；Ekman 输运与风应力成正比、与科氏参数成反比，北半球偏向风向右侧 90°，南半球偏左。上升流指数取输运在离岸法向上的分量，海岸走向是站点属性。可以核对的数：风应力 0.1 N/m²、海水密度 1025 kg/m³、纬度 45° N 时，输运约 0.946 m²/s；涡粘系数取 0.01 m²/s 时，Ekman 层深度约 43.8 m，表层流速约 0.096 m/s、方向在风向右侧 45°。必须成立：风应力加倍输运加倍；纬度取相反数时输运大小不变、偏转方向反号；风向与海岸平行且海岸在风向左侧（北半球）时上升流指数为正。赤道附近科氏参数趋于零，理论不再适用，纬度绝对值小于某个阈值的站点要明确标为不适用，阈值进配置，不能算出一个巨大的数。

数据以小时记录进入，每条带站点、时刻、风速、风向和来源批次。服务的核心是"汇总作业"：选定站点集合与时间范围，产出每个站点的逐日、逐月指数以及区域平均。站点缺测时，日值要给出有效小时数，低于门限的日值标为不足、不参与月均；区域平均只纳入当日有效的站点，并报告纳入了哪些。批内某个站点配置有误（缺海岸走向、纬度越界），只让它失败并说明原因，其余站照常出结果。

数据会持续追加，也会被整段更正。对已有作业的时间范围追加或更正数据后，再次提交同一作业应只重算受影响的日和月，结果必须与把全部有效记录从头汇总完全一致。是保存小时级中间量、只存日值再回推，还是存别的形式，存多少换算多少，由你权衡并在文档里给出存储量和重算量的估计。作业可以查进度、取消；服务中途重启后，未完成的作业从已完成的部分接着做，最终结果与不中断一致。每次作业结果保留，能查某个月的指数在哪次作业里因为哪批数据发生了变化。

需要拒绝：风速为负、风向不在 [0,360)、密度或涡粘系数非正、时间范围起点不早于终点、同一站点同一时刻两条来源不同且数值不同的记录（作为冲突报出，不随意取一条）。

用 Node.js 20 + TypeScript，Web 框架 Express；风记录、站点、作业与结果都放在 MongoDB 7。应用容器以 node:20-slim 为底，数据库用 mongo:7，两个服务写进 compose 文件。风应力与输运计算、站点与海岸几何、日月汇总、增量重算、作业调度、持久化与 HTTP 层分模块组织；用 Jest 或 Vitest 验证参考数值、加倍与南北半球对称、赤道带不适用、缺测门限与区域平均的纳入规则、单站失败隔离、追加与更正后增量结果和全量一致以及重启续做一致。
